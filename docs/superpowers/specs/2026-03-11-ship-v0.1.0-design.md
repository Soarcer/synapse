# Ship Synapse v0.1.0 — Design Spec

**Date:** 2026-03-11
**Author:** Bernhard (with Claude)
**Status:** Approved

## Problem Statement

Synapse is a fully functional agent monitoring dashboard with a VS Code extension, server, and React frontend. It has 34 test files, comprehensive docs, and a working build pipeline. But it has never been publicly released. The codebase carries AGPL licensing, an enterprise /ee directory, inconsistent version numbers, and no publishing infrastructure.

**Goal:** Ship Synapse as a public, MIT-licensed open-source project with two distribution channels:

1. VS Code extension (Marketplace + Open VSX + GitHub Releases)
2. npm CLI (`npx @synapse-ai/cli`) for terminal Claude Code users

**Non-goals:**

- Revenue or monetization (fame/recognition is the primary goal)
- Multi-provider support (Claude-focused)
- OpenClaw plugin in v0.1.0 (deferred, but validated during this exercise)

## Key Decisions

| Decision        | Choice                                                 | Rationale                                                                                  |
| --------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| License         | MIT                                                    | Maximum community goodwill. Same as OpenClaw (closest peer). No friction for contributors. |
| Distribution    | VS Code Marketplace + Open VSX + GitHub Releases + npm | Maximum reach across all channels.                                                         |
| Testing bar     | E2E + VS Code extension tests                          | High confidence before going public.                                                       |
| Enterprise /ee  | Remove entirely                                        | Pure MIT, no dual-license complexity.                                                      |
| OpenClaw plugin | Defer from v0.1.0                                      | Validate it works, but don't include in initial release.                                   |
| Version         | v0.1.0                                                 | "Early but usable." All packages normalized to same version.                               |
| CLI experience  | `npx @synapse-ai/cli`                                  | Zero-install. Runs server, opens browser dashboard.                                        |

**Performance & Memory Leak Audit (time-boxed: 4 hours):**

Acceptance criteria — must pass to ship:

- Server heap usage plateaus (does not grow >20% over 30 minutes of continuous events)
- Dashboard renders 100+ nodes at >30fps
- No WebSocket connection leaks after 10 connect/disconnect cycles
- CLI/extension shutdown leaves no orphaned node processes
- Dashboard bundle size <5MB (gzipped)

Findings that don't meet thresholds are filed as GitHub issues for post-v0.1.0, not blockers.

- Server long-running stability test:
  - Run server for extended period with continuous simulated events
  - Monitor Node.js heap usage (`process.memoryUsage()`) over time — heap should plateau, not grow linearly
  - Check for WebSocket connection leaks (disconnected clients still held in memory)
  - Check for SQLite/sql.js memory growth — sql.js keeps the entire DB in memory with no size guard. Consider adding an event retention limit (e.g., keep last 10,000 events, prune older) or document this as a known limitation <!-- revised: P1 from architect review -->
  - Verify event listener cleanup on session end (EventEmitter leak detection)
- Dashboard performance audit:
  - React Flow rendering with 100+ nodes — measure frame rate, identify jank
  - Zustand store subscription leaks (components mounting/unmounting)
  - Check for detached DOM nodes using Chrome DevTools Memory panel
  - Verify `useEffect` cleanup functions run on unmount (WebSocket listeners, intervals, timeouts)
  - Bundle size analysis (`vite-plugin-visualizer`) — identify unexpectedly large chunks
- VS Code extension:
  - Webview disposal — verify server shuts down when panel closes
  - Extension deactivation — no orphaned processes after VS Code closes
  - Memory usage of embedded server within VS Code's Node.js process
- CLI:
  - Graceful shutdown on SIGINT/SIGTERM — no zombie processes
  - Port cleanup — verify port is released after shutdown
  - File handle cleanup (SQLite DB, log files)
- Tooling:
  - Add `--inspect` flag support to CLI/server for heap profiling
  - Consider `clinic.js` (Doctor + Flame) for automated performance analysis
  - Add a stress test script: `scripts/stress_test.ts` that floods the server with events and monitors memory

## Risks & Mitigations

| Risk                                                        | Mitigation                                                                                                      |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| VS Code Marketplace review rejection                        | Follow all marketplace guidelines; test on multiple OS before submitting                                        |
| npm scope `@synapse-ai` unavailable                         | Day 0 check. Backup: `@synapse-dash` or unscoped `synapse-cli`                                                  |
| CLI bundle too large                                        | Dashboard static files add size; consider lazy download on first run if >20MB                                   |
| Breaking changes to Claude Code hooks API                   | Hook scripts are simple POST relays; easy to update. Pin to known hook event schema.                            |
| Open VSX publishing delays                                  | Open VSX reviews can take time; publish to Marketplace first                                                    |
| `@vscode/test-electron` flaky on CI                         | Budget extra time; consider running only on ubuntu in CI                                                        |
| VS Code Marketplace first-time review                       | Can take 1-5 business days with possible iterations. Submit early.                                              |
| openclaw `better-sqlite3` breaks `pnpm install` on clean CI | Exclude openclaw from workspace or make its deps optional                                                       |
| sql.js in-memory DB unbounded growth                        | Add event retention limit (10K events) or document as known limitation. Monitor in perf audit. <!-- revised --> |
| Partial npm publish failure                                 | Only publishing 1 package (@synapse-ai/cli) now, so this risk is eliminated. <!-- revised -->                   |

## Open Questions / Deferred (P2)

<!-- P2 findings from review — not blocking v0.1.0, address post-launch -->

- **First-run experience for CLI**: If no Claude Code session is active, dashboard shows empty state. Consider auto-running `simulate_session.ts` on first launch so users see something immediately.
- **Launch strategy**: Publishing to registries is necessary but not sufficient for recognition. Consider: Hacker News post, r/ClaudeAI, dev.to article, Twitter/X thread. Plan this separately from the code work.
- **Changelog tooling**: For ongoing releases, consider `changesets` or conventional-commits-based tooling. For v0.1.0, manual release notes are fine.
- **DCO enforcement**: CONTRIBUTING.md requires DCO sign-off but there's no automated check. Consider adding `probot/dco` GitHub Action post-launch.
- **Re-publish `@synapse-ai/core` and `@synapse-ai/server`**: If external consumers want to build on Synapse's types or server, these can be published later. Not needed for v0.1.0.
