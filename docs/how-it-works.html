How Synapse Works

Hooks, servers, ports, and the glue between them
← Back to README

The Big Picture

Synapse is a parasite. A friendly one. It attaches to your Claude Code session via hook scripts, silently captures every event, and pipes them to a local server that your browser connects to. Claude Code doesn't know Synapse exists. It just thinks it's running hooks.

Three moving parts. That's it.

architecture ┌──────────────────┐ stdin (JSON) ┌──────────────────┐ │ │ ───────────────────▶ │ │ │ Claude Code │ │ Hook Script │ │ (your session) │ HTTP hook (blocks) │ send_event.cjs │ │ │ ◀─────────────────── │ │ └──────────────────┘ └────────┬─────────┘ │ POST /api/events (fire & forget) │ ▼ ┌───────────────────────────────────────────────────────────────┐ │ Synapse Server :27246 │ │ │ │ ┌─────────────┐ ┌──────────────┐ ┌──────────────────┐ │ │ │ Event Router │──▶│ SQLite Store │──▶│ WS Broadcaster │ │ │ │ + Adapters │ │ (sql.js) │ │ (real-time push) │ │ │ └─────────────┘ └──────────────┘ └────────┬─────────┘ │ │ │ │ │ ┌──────────────────────────────────────────┐ │ │ │ │ Permission Server :27247 │ │ │ │ │ (holds HTTP response until user decides) │ │ │ │ └──────────────────────────────────────────┘ │ │ └──────────────────────────────────────────────────┼────────────┘ │ WebSocket │ ┌─────────────────────┼──────────────────┐ ▼ ▼ ▼ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ VS Code │ │ Browser │ │ Phone │ │ WebView │ │ localhost │ │ PWA │ └──────────────┘ └──────────────┘ └──────────────┘

The flow: Claude Code fires a hook → hook script reads JSON from stdin → POSTs it to the server → server normalizes, stores, broadcasts → dashboard renders it as a node in the graph. Total latency: under 50ms.

Part 1: The Hooks

Claude Code has a hooks system. You register scripts in .claude/settings.local.json, and Claude Code runs them at specific lifecycle moments — session start, tool calls, permission requests, context compaction, etc.

Synapse registers two types of hooks per event:

Command Hooks (fire-and-forget)

Claude Code pipes the event as JSON to stdin. The hook script reads it and POSTs to the Synapse server. Three-second timeout. Always exits 0. If the server is down, the event is silently dropped — Claude Code never notices.

// hooks/send_event.cjs — the entire logic
const data = JSON.parse(require('fs').readFileSync('/dev/stdin', 'utf8'));
const url = discoverPort();  // .synapse-port → ~/.synapse/port → default
http.request(url, { method: 'POST', timeout: 3000 }, () => {}).end(JSON.stringify(data));

Zero dependencies. Pure Node.js. Runs in the same process as Claude Code's hook executor.

HTTP Hooks (bidirectional — permissions only)

This is the clever part. For PermissionRequest events, Claude Code supports HTTP hooks — it POSTs to a URL and waits for the response. Synapse holds that response open until you approve or deny from the dashboard. Claude Code just... sits there, blocking, until you decide.

// In .claude/settings.local.json
"PermissionRequest": [{
  "hooks": [
    { "type": "command", "command": "node hooks/send_event.cjs" },
    { "type": "http", "url": "http://localhost:27247/api/hooks/permission", "timeout": 1800 }
  ]
}]

The command hook captures the event for the dashboard. The HTTP hook blocks Claude Code until you respond. Two hooks, one event, two different purposes.

Why settings.local.json? Because it's gitignored. Your Synapse hooks are local to your machine — they don't pollute the shared settings.json that your team checks in.

Part 2: The Server

One Node.js process. Two HTTP servers. One WebSocket. One SQLite database. No external services.

Main Server — :27246

Express 5. Handles everything except permission blocking:

  • POST /api/events — Hook scripts send events here. The server runs them through an adapter registry (Claude, Gemini, or Codex adapter), deduplicates within a 2-second window, persists to SQLite, and broadcasts to all connected dashboards via WebSocket.
  • GET /api/events — Query stored events. Filter by session, agent, type, time range, project directory.
  • /api/agents/* — Spawn, message, stop, and inspect agents via the Claude Agent SDK.
  • /api/permissions/* — List pending permissions, submit approve/deny decisions.
  • /api/analytics/* — Aggregated stats — KPIs, session breakdowns, tool usage, cost tracking.
  • WS /ws — Real-time event stream to the dashboard. Heartbeat every 30s. Backpressure detection — if a client falls behind (>64KB buffered), it gets a stale signal to trigger a full reload.

Permission Server — :27247

Separate HTTP server, single endpoint. This is the one that makes remote approval work.

permission flow Claude Code Hook Server :27247 Dashboard │ │ │ │ POST /api/hooks/permission │ │ │ ────────────────────────────▶│ │ │ │ WS: pendingPermission │ │ (HTTP response held │ ──────────────────────────▶│ │ open... waiting...) │ │ │ │ │ User taps │ │ POST /api/permissions/ │ "Approve" │ │ {id}/respond │ │ │ ◀──────────────────────────│ │ 200 OK { decision: allow } │ │ │ ◀────────────────────────────│ │ │ │ │ │ (Claude Code resumes) │ │

The response shape matters. Claude Code expects a specific format:

{
  "hookSpecificOutput": {
    "hookEventName": "PermissionRequest",
    "decision": {
      "behavior": "allow"    // or "deny"
      "message": "..."       // optional context for deny
    }
  }
}
30-minute timeout. If nobody responds, the permission auto-denies. Rate-limited to 60 requests/minute to prevent runaway agent loops from flooding the queue.

SQLite — Pure JavaScript

We use sql.js instead of better-sqlite3. No C bindings. No WASM file. No native compilation step. It's slower, but it installs on every platform without a compiler, which matters when you're shipping a VS Code extension to people who may not have build tools.

The database lives at packages/server/synapse.db (or ~/.synapse/synapse.db in daemon mode). Delete it to start fresh. Persistence is debounced — after each write, the in-memory database exports to disk on a 500ms delay.

Adapter Registry

Not all hook events look the same. Claude Code, Gemini CLI, and Codex CLI each have their own event format. The adapter registry normalizes them:

AdapterDetects ByInput Format
Codexcodex_source fieldJSON from CLI arg (not stdin)
GeminiGemini-specific hook fieldsJSON from stdin
Claudehook_event_name (catch-all)JSON from stdin

First match wins. Every adapter outputs the same AgentEvent type, so the rest of the pipeline — storage, broadcasting, rendering — doesn't care which vendor generated the event.

Part 3: Finding the Server

The hook scripts need to know where to POST events. The server might be on port 27246, or 27247, or 27266 because 20 other things were already running. So Synapse uses a port file system:

Port Discovery Chain

When a hook script fires, it checks these locations in order:

  1. SYNAPSE_URL env var — full URL override (rare)
  2. .claude/.synapse-port — project-local file, written by CLI or VS Code extension when it starts
  3. ~/.synapse/port — global daemon port, written by synapse start or VS Code
  4. Default — http://localhost:4000/api/events (fallback, rarely hit)

When the server starts, it tries port 27246. If that's busy, it increments and tries up to 20 ports. Whatever port it lands on gets written to the port files. The hook scripts read it at runtime. No hardcoded ports anywhere in the hook configuration.

This means you can run multiple instances. VS Code with one project on :27246, CLI daemon for another on :27247. Each project's .synapse-port file points to the right server. Hook scripts just read the file and POST.

Part 4: VS Code vs. CLI

Same server. Same dashboard. Different packaging.

VS Code Extension

The extension bundles the server as a single server.mjs file (esbuild, ESM). On activation:

  1. Check if a daemon is already running (~/.synapse/port + health check)
  2. If yes → attach to it. Don't start a new one, don't stop it on deactivate.
  3. If no → spawn node resources/synapse-server/server.mjs as a child process
  4. Read SYNAPSE_PORT=NNNN from stdout to learn the actual port
  5. Write port to .claude/.synapse-port and ~/.synapse/port
  6. Configure hooks in .claude/settings.local.json (absolute paths to bundled hook scripts)
  7. Open dashboard in a webview panel

When VS Code closes, the child process dies with it. No orphaned servers.

CLI (synapse start)

The CLI builds into a standalone npm package with the server, dashboard assets, and hook scripts bundled in.

  1. synapse start — start server, auto-scan for free port, configure hooks for current project
  2. synapse start --bg — detach as background daemon. PID written to ~/.synapse/pid
  3. synapse stop — graceful SIGTERM with 10-second force-kill fallback
  4. synapse status — check if running, print dashboard URL
  5. synapse hook / synapse unhook — add or remove hooks for any project directory

One daemon can serve multiple projects. Each project gets its own hook config pointing to the shared server. Events are tagged with cwd so the dashboard can filter by project.

Both modes write to the same port files. If you start the CLI daemon first, then open VS Code, the extension will detect the daemon and attach to it instead of spawning its own server. One server, however many clients you want.

Part 5: The Dashboard Connection

The dashboard connects via WebSocket to ws://localhost:{port}/ws. On connect:

  1. Server sends a connected message with the list of active agents
  2. Dashboard fetches recent events via GET /api/events?limit=2000 to hydrate the graph
  3. From then on, new events arrive as WebSocket messages in real-time

Message Types

TypeDirectionPurpose
connectedserver → clientInitial handshake, active agents list
eventserver → clientNormalized AgentEvent (the main data)
pendingPermissionserver → clientPermission card should appear
permissionResolvedserver → clientPermission was approved/denied
agent_textserver → clientStreamed agent output (spawned agents)
staleserver → clientClient fell behind — reload everything
Backpressure. If a client's WebSocket buffer exceeds 64KB (slow network, big burst of events), the server stops sending and marks it stale. When the buffer drains, it sends a stale signal. The dashboard responds by fetching all events fresh from the HTTP API. No lost events, just a brief pause.

Heartbeat pings every 30 seconds. If a client doesn't respond, it gets disconnected. On mobile (iOS Safari is particularly aggressive about killing background WebSockets), the dashboard auto-reconnects with exponential backoff. If it was stale, it rehydrates. The user sees a brief "reconnecting..." indicator and then everything's back.

Putting It All Together

Here's what happens when you type a prompt in Claude Code and an agent calls a tool:

event lifecycle You type "refactor the auth module" │ ▼ Claude Code fires UserPromptSubmit hook │ ├─▶ send_event.cjs reads stdin JSON │ └─▶ POST localhost:27246/api/events │ └─▶ ClaudeAdapter.normalize() → AgentEvent │ └─▶ SQLite INSERT + WS broadcast │ └─▶ Dashboard: new "prompt" node appears │ ▼ Claude spawns a subagent → SubagentStart hook │ └─▶ (same flow) → Dashboard: new "agent" node, edge animates in │ ▼ Agent calls Read tool → PreToolUse hook (async) │ └─▶ Dashboard: tool node appears in "running" state │ ▼ Read succeeds → PostToolUse hook (async) │ └─▶ Dashboard: tool node turns green, duration badge updates │ ▼ Agent needs to write a file → PermissionRequest hook │ ├─▶ send_event.cjs → event captured for dashboard │ └─▶ HTTP hook → POST localhost:27247/api/hooks/permission │ (Claude Code blocks here) │ └─▶ Server holds response, broadcasts pendingPermission └─▶ Dashboard: permission card appears Phone: push notification fires │ ▼ You tap "Approve" on your phone │ └─▶ POST /api/permissions/{id}/respond └─▶ Server resolves held HTTP response └─▶ Claude Code resumes writing the file

Every step produces an event. Every event becomes a node or updates a node. The graph is a real-time mirror of what Claude is actually doing.
